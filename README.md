# Fieldnotes — AI Research Assistant

Fieldnotes is a local-first research workspace for organizing research projects and files, searching scholarly papers, and asking questions grounded in your sources. The web client is React + TypeScript; the API is FastAPI; PostgreSQL stores research and literature data, with pgvector for document embeddings. Local development uses separate research and literature databases; hosted deployments may use one database or separate URLs.

See [ARCHITECTURE.md](ARCHITECTURE.md) for the implemented system architecture, integrations, API surface, data flows, and complete user feature inventory.

## What is implemented

- Account registration with a unique username, 12+ character password checks, login, signed bearer tokens, and owner-controlled project sharing.
- Open **Profile & settings** from the account control in the lower-left sidebar. The **Profile** page lets you view your email, change your display name and username, upload a resized profile picture, and securely change your password. Separate **AI usage** and **Notifications** pages show daily allowances/document-processing status and let you choose which project events create new in-app alerts. All notification categories are enabled by default; changing preferences does not remove existing inbox items. Passwords are one-way hashed and cannot be revealed.
- Sign-in throttling: 5 attempts per IP/email pair and 30 attempts per IP in a 15-minute window, with hashed identifiers and automatic reset after successful sign-in.
- Account and project data persist in PostgreSQL across logout/login and normal Docker restarts; logging out clears the local session token, not the account.
- Source comments and saved-paper/document highlights are stored in the PostgreSQL `annotations` table with their author, tags, pin state, and links to other project sources, not in browser storage or the original file. Readers can view; commenters can add comments and edit their own; project owners can moderate all comments. Annotation notes support collaborator @mentions, validated against the project roster, with in-app notifications for newly mentioned collaborators.
- Research project create/list/update/delete, private document storage, and project-level document text search.
- A project **Overview** shows recent project changes, documents that still need processing attention, open tasks, and up to six recently opened papers or documents. Empty projects include guided actions for uploading documents, finding papers, and asking the assistant. The sidebar also provides cross-project **Quick access** to pinned sources and the six most recently viewed sources. Pin or unpin a source from its sidebar row; quick-access data is private to the signed-in user and stored in this browser.
- **Search all projects** finds saved papers and documents across every project the signed-in user can access, with project, source type, author, year, and exact-tag filters.
- Add and edit project-scoped tags and custom string metadata on documents and saved papers; filter either library by tags or metadata fields and values.
- Organization team workspaces with multiple shared projects, registered-member invitations, and workspace-wide or project-scoped messaging channels.
- Share projects with registered colleagues by username or email and assign **Reader**, **Commenter**, or **Editor** access. Readers can view and compile; commenters can also add source comments; editors can change shared project content. Owners manage roles and access. Assistant conversation histories remain private to each author.
- Lightweight source-linked team tasks can be assigned to project collaborators, optionally attached to a note, tracked as open/in progress/done, and reassigned by the creator or project owner. Assignees receive in-app notifications.
- In-platform direct messages and an inbox for project invitations, invitation responses, messages, saved-search alerts, annotation mentions, and task assignments. Choose which of these event categories create new inbox notifications in **Profile & settings → Notifications**; disabled categories do not affect the underlying invitations, messages, searches, notes, or tasks. Existing inbox items remain available. Notifications and shared-project content refresh automatically while the workspace is open.
- A persistent per-project LaTeX writing workspace with automatic saving, citation-key checks, searchable saved-paper citation insertion, `plainnat`, `abbrvnat`, `unsrtnat`, and `apalike` bibliography styles, custom installed `.bst` style names, and sandboxed PDF compilation with a 20-second timeout and 25 MB output limit. The lightweight article preview remains a separate, non-TeX preview.
- PDF, DOCX, TXT, and Markdown upload and extraction. Scanned PDF pages are processed with Tesseract OCR. Files are limited to 25 MB by default and PDFs to 100 pages.
- Bulk document upload accepts up to 20 files per request and clearly shows when each file is uploading, extracting text, ready, or needs attention. Failure details include next steps, and failed items can be retried. Once files have been accepted and saved by the API, extraction continues in the background if the browser window closes; status and retry controls remain available in the project document list.
- Open **Work status** in the project toolbar to follow uploads, document extraction/indexing, and LaTeX compilation together from any project section. It shows current work, actionable failures, and a few recent completions; server-side document processing status refreshes while the workspace is open.
- Open an uploaded document to read its extracted text and view its highlights and notes in the document reader. On saved papers, annotate the available abstract; notes persist across sessions.
- The project-wide **Notes** view searches saved document/paper annotations and tags, filters by source or pinned status, and keeps pinned notes first. Comment authors and project owners can tag and pin notes and link them to other saved papers or project documents; each related-source link opens that source. Mention collaborators in notes with `@username`; assign source-linked review tasks with optional note links, and track their status in Notes. You can also select notes to add as clearly labeled, untrusted context to an assistant source comparison.
- Global keyboard shortcuts open cross-project search (`Ctrl/Cmd+K`), create a source-linked note (`Ctrl/Cmd+Alt+N`), open document upload (`Ctrl/Cmd+Alt+U`), and switch project sections (`Ctrl/Cmd+Alt+1` through `7`, in tab order). They are ignored while editing text or while a dialog is open. Creating notes requires comment access; uploads require editor access.
- **Summarize** actions in Literature and Notes open a concise AI summary for a saved paper or annotated source. Paper summaries use imported full text when available and otherwise the abstract; document summaries use extracted text. The project reuses each summary for the same source and summarization-policy version, and refreshes it when either changes. Summaries are prompted to preserve study-group, outcome, and comparison qualifiers and to omit ambiguous details rather than infer them; review the source for critical decisions.
- Document chunking and OpenAI embeddings, stored in pgvector.
- Page-level citations for PDF evidence: assistant citations identify the source document, PDF page, and supporting passage; opening a citation displays the original PDF at that page. Reprocess PDFs that were already processed before this feature to add page locators to their existing chunks.
- OpenAlex and Crossref literature search with semantic re-ranking of paper abstracts when an OpenAI key is configured, cached paper and author metadata, query history, and saving/removing papers from projects. Before saving a result, Literature compares its DOI and normalized title with papers already in the project and prompts for review of possible duplicates or related titles, including records with missing or differing metadata. Users can cancel or save both records; suggestions never merge or block papers.
- Project-shared collections group saved papers and project documents into named sets such as “Background,” “Methods to reuse,” or “Read next.” Editors can create, rename, and delete collections, add or remove sources, and open a collection item in its original library.
- Project-scoped saved literature searches can be rerun and optionally checked for new results. In-app alerts are checked every six hours while the selected project is open; checks pause when the app is closed, and no email alerts are sent.
- Import RIS and BibTeX bibliographies into a project and export its saved references in either format. DOI matching prevents a reference already in the project from being added twice; records without a DOI remain separate.
- Import OpenAlex-confirmed open-access PDFs for saved literature papers. Imported papers use the existing extraction, chunking, and embedding pipeline so their full text can be read, searched, and queried with the assistant.
- Project systematic-review workspace: save a project-shared review question and protocol, screen saved papers as unread, undecided, include, or exclude, filter by decision or publication year, bulk-apply decisions, and track counts for all four outcomes. Export a review report CSV with the question, protocol, decision counts, and each paper's metadata, decision, and note. Undecided papers count as reviewed.
- Review handoffs: editors can assign each paper to multiple collaborators with commenting or editing access. Assigned commenters can submit their independent screening decisions, and the workspace shows assigned-versus-screened progress by person. Removing an assignment preserves that reviewer's decision history.
- Use the **Python analysis** section in the **Writing & analysis** project-files column to create and edit up to 20 project-shared `.py` files in a CodeMirror editor with Python syntax highlighting. Run the selected script with pandas, NumPy, Matplotlib, and Jinja2 in a browser Web Worker using Pyodide; helper modules in the same workspace can be imported. Optionally select CSV/TSV inputs for the current run. When outputs are saved, the project also stores that run's timestamp, exact script/helper source snapshot, and exact selected input-file contents so collaborators can inspect and download the run record. These local inputs are uploaded only when the run produces saved outputs; treat them as shared project data. Run snapshots are capped at 100 MB per project. Generated PNG, CSV, TSV, and TeX files are saved with the project, can be inserted into LaTeX as figures or tables, and are included in project exports. Inserting a TeX table automatically loads `booktabs` when needed, including for pandas' default `DataFrame.to_latex()` output. Python never runs on the API server.
- LaTeX is the writing workspace in **Writing & analysis**. Open Python analysis from the project-files column, switch scripts with the clearly labeled Python files buttons above the editor, and use **Back to LaTeX** to return to writing.
- Export a project ZIP with project details, references in JSON/RIS/BibTeX, source notes, LaTeX and Python writing files, generated outputs, review protocol, and a document inventory. Original uploads and the requesting user's assistant conversations are separate opt-in choices; collaborators' conversation histories are never included.
- Export a selected research packet as a ZIP with up to 100 saved papers, 500 project notes, and 100 approved assistant responses, plus references and source citations. Assistant outputs are limited to the requesting user's own approved messages; other collaborators' private conversation histories are excluded.
- Project conversations with question, comparison, and research-direction modes. Retrieval combines relevant document chunks and saved-paper abstracts; prompts asking to find a paper also search OpenAlex and show retrieved results as linked chat sources.
- Choose the project documents and saved papers to include in each assistant question; automatic retrieval remains available, and manual source selection disables external paper discovery for that question.
- Assistant `[S#]` citations open their matching evidence. PDF source cards show the cited page and supporting passage and open the original PDF at that page; non-PDF citations open the document reader at the highlighted passage, even when extraction changed its whitespace.
- Flag a weak citation in the source card or request a new draft that excludes that source and uses other selected project evidence. Citation flags are temporary and are not saved to the conversation.
- Assistant answers are built from atomic claims with verbatim source quotes, checked for an exact excerpt match, and passed through a second evidence-support and question-completeness review. Unsupported claims are omitted; if only part of the question is verified, the answer flags that limitation, and if no claims pass, it abstains. This reduces hallucination risk but cannot guarantee zero errors, so human review remains required.
- **Compare sources** produces a source-by-source evidence matrix for each study's research question, methods, sampling, findings, and limitations. Every supported claim retains a clickable source citation; fields not established by the retrieved excerpts are marked **Missing evidence** rather than inferred.
- Export an approved source comparison as an editable Word research brief with a cited findings synthesis, the evidence matrix, and a bibliography for every cited paper or document. Missing-evidence markers and source citations are retained so the brief can be reviewed and revised before sharing.
- Assistant drafts are limited to 50 prompts per client IP per UTC day. **Profile & settings** shows prompts remaining, a 50,000 estimated embedding-token allowance per account per UTC day, and document-processing status totals. The embedding cap includes initial uploads, open-access imports, and reprocessing; when reached, extracted text is retained and documents can be retried after reset. Set `DAILY_EMBEDDING_TOKEN_LIMIT` in `.env` to change the per-account cap.
- Separate administrator sign-in with an allowlisted account, user/account summaries, metadata-only activity history, and permanent account deletion.
- A mandatory human approval step: generated answers and conversation messages are not saved until **Approve & save** is clicked. Draft approval tokens are signed, user/project-bound, expire after 15 minutes, and are idempotent.
- Docker Compose setup, API health endpoint, interactive API docs, and focused backend tests.
- API security headers, HTTPS-only HSTS, and non-cacheable API responses.

## Run locally with Docker

You need Docker Desktop with Docker Compose enabled. From the repository root in PowerShell:

```powershell
Copy-Item .env.example .env
```

Edit `.env` before starting:

1. Replace `POSTGRES_PASSWORD` and `JWT_SECRET` with private random values. Use letters and digits only for `POSTGRES_PASSWORD` (for example, generate a hex value with `python -c "import secrets; print(secrets.token_hex(32))"`); the password is included in a database URL.
2. Set `OPENAI_API_KEY` to your own OpenAI API key. Keep it in `.env`; **do not paste it into chat or commit it**. OpenAI usage may incur charges.
3. Optionally set `OPENALEX_API_KEY` to use your OpenAlex account's higher API budget, and `OPENALEX_EMAIL` to identify polite requests. Keep the key in `.env`; do not paste it into chat or commit it.
4. Optionally set `DAILY_EMBEDDING_TOKEN_LIMIT` to change the default 50,000 estimated embedding tokens per account per UTC day.

Then start the stack:

```powershell
docker compose up --build
```

Open the app at <http://localhost:5173>. The API health check is at <http://localhost:8000/api/health>, and interactive API documentation is at <http://localhost:8000/docs>.

Create an account with a username. Select your account name or profile picture in the lower-left sidebar to open **Profile & settings**. Use **Profile** to edit your display name and username, upload a profile picture, view your sign-in email, or securely change your password; **AI usage** shows daily allowances and document-processing status, and **Notifications** lets you enable or disable each in-app event category. Select the team-workspaces control to create an organization workspace and invite registered members by username or email. Switch workspaces in the sidebar, create multiple projects inside a team workspace, and use **Team channels** for workspace-wide discussion or a channel restricted to the selected project. Project owners can still invite registered people outside the organization to a single project; those guests can use that project's channel but cannot see workspace-wide channels. Invitations are accepted from the team-workspaces panel. Use a project's share icon to assign or change a collaborator's Reader, Commenter, or Editor role. Shared project data and the LaTeX workspace refresh in the background while open; concurrent LaTeX edits are protected from silently overwriting a newer saved version.

## Getting around

Use the left sidebar to switch workspaces and projects, return to pinned or recently viewed sources across accessible projects, or open **Search all projects**. Quick access is stored per user in this browser; pinning does not change project sharing or make a private item visible to collaborators. Global search finds saved papers and documents across projects you can access; filter by project, source type, author, year, or exact tag, load more results as needed, then open a result in its project. The **Recent search records** list saves your exact query, active filters, search time, result count, and project-library provider; rerun a record to apply the same query and filters again. Inside a project, **Overview** summarizes recent changes, processing issues, open tasks, and recently opened sources. Empty projects show guided actions to upload documents, find papers, or start with the assistant. The recent-source list is also saved in this browser, separately for each signed-in user and project. Project sections are **Overview**, **Documents**, **Literature**, **Collections**, **Notes**, **Writing & analysis**, and **AI assistant**. On tablet and phone, choose a section from the labeled **Project section** selector rather than scrolling through tabs; less-frequent team and project actions are grouped under **More**. Use **Collections** to group project papers and documents into shared named sets, add or remove sources, rename or delete a collection, and open its sources in the project library. The project toolbar includes **Work status** for active uploads, document processing, LaTeX compilation, failures, and recent completions. Keyboard shortcuts are available outside text fields: **Ctrl/Cmd+K** searches all projects; **Ctrl/Cmd+Alt+N** opens the source-linked new-note form; **Ctrl/Cmd+Alt+U** opens document upload; **Ctrl/Cmd+Alt+1–7** switches the project section in tab order. On a phone, use the menu button at the top left to open the navigation drawer; choose a workspace, project, quick-access source, or global search, then press **Close navigation**, tap outside the drawer, or press Escape to dismiss it. In Python Analysis, the file selector switches scripts; adding or editing files requires Editor or Owner access, and read-only collaborators see that restriction explained inline.

Upload documents and search OpenAlex or Crossref for papers. In **Literature**, new completed queries are saved to project search history with their exact query, provider, search time, result count, and maximum-results setting; use **Rerun** to repeat a recent search. Older history entries retain their available query, provider, date, and result count, but may show filters as not recorded. You can also save a query/provider for easy reruns and optionally enable alerts for new matches. Alert checks run at most once every six hours while that project is selected in the open app and create in-app inbox notifications; they pause when the app is closed. No email alerts are sent. In the same view, the **Systematic review workspace** lets editors save a project-shared review question and protocol; all project collaborators can read them. The **Study extraction matrix** provides one shared row per saved paper for population, methods, sample size, outcomes, and limitations; editors can update rows, collaborators can read them, and both review CSV exports include the extraction fields. For each saved paper, editors can record an independent decision under their own identity, with a timestamp and structured exclusion reason; “Other” requires a note. Reviewer decisions remain distinct from the project-level adjudication. Conflicting reviewer outcomes or exclusion reasons are flagged on the paper and in the disagreement count, while the reviewer decision trail shows names, decisions, reasons, notes, and timestamps. Filter saved papers by adjudicated decision, publication year (including unavailable years), or searchable metadata, and sort by title or publication year. Add reusable tags and custom string key/value metadata to documents and saved papers; use the library filters to narrow either list by tag or metadata field/value. Select papers individually or select the visible filtered results, then apply a bulk adjudication; existing notes are preserved. **Export review report** downloads a CSV containing the saved question and protocol, total/reviewed counts, counts for each adjudication, and each paper's metadata, screening trail, and study extraction; **Export screening CSV** includes the extraction fields alongside paper rows. Undecided papers count as reviewed but remain distinct from included and excluded papers. The imported PDF appears in Documents and, after processing, its text is available for document search and assistant questions. If no open-access PDF is available, upload a copy you have access to. Open a document from the Documents list to read its extracted text, highlight passages, and comment; use **Annotate** on a saved paper to comment on its available abstract. Use `@username` in annotations to notify project collaborators. In **Notes**, create tasks linked to a paper or document, optionally attach a note, assign a collaborator, and update progress; the task creator or project owner can reassign or delete a task, while assignees can update status. Task assignments and new mentions appear in the inbox and link back to project Notes. Use **Summarize** on a saved paper or a note to open a project-shared AI summary; summaries use imported full text when available, are saved by source content version, and are reused on repeat visits. In project **Notes**, search or filter notes, pin important ones, add comma-separated tags, link them to other saved papers or project documents, and open those linked sources directly. Select notes to add to a **Compare sources** prompt as untrusted researcher context—not evidence. Notes, tasks, summaries, and screening decisions persist in the project database across sessions. Open **Writing & analysis** to edit `main.tex` and `references.bib`, choose a bibliography style or enter an installed custom `.bst` style name, check for missing/duplicate citation keys, and compile a real PDF. Search saved literature by title, author, year, DOI, venue, tags, or metadata, then insert a BibTeX entry and citation (or an abstract with its citation). Use **History** to compare earlier versions side by side with the current working copy and restore up to 20 saved versions per file. Python analysis provides the same compare-and-restore history for each script, including scripts removed from the current workspace. Compiler diagnostics with a source line can jump directly to that line in the editor. Use **Python analysis** in the Writing & analysis project-files column to create multiple related `.py` files, run the selected script with helper modules, and generate figures or tables in the browser. Each output records the run time and selected script; its run record retains the exact entry script, helper modules, and CSV/TSV contents, which can be inspected or downloaded in the output card. The source/preview/split layouts include a lightweight structural preview, explicitly separate from the TeX compiler; compiled PDFs appear in the PDF view. Ready project documents can load editable excerpts. The API Docker image provides `pdflatex` and BibTeX; compilation runs without shell escape as a separate unprivileged user, with time and output limits. OpenAI is required for semantic literature re-ranking, document embeddings, assistant answers, and AI summaries. Without an OpenAI key, academic search still returns provider-ranked results, uploads are retained, and document text can still be searched; documents show **Needs API key** and can be reprocessed after you add a key and restart the API. In chat, ask to find or pull up a paper to search OpenAlex and include relevant paper abstracts and links in the draft. Assistant `[S#]` citations link to their source cards; PDF evidence shows the cited page and passage and opens the original PDF at that page.

To create a cited research brief, choose **Compare sources**, review and approve the draft, then select **Export cited brief** on the saved comparison. The editable Word document includes a findings synthesis, the evidence matrix, and bibliography; its `[S#]` markers connect claims to bibliography entries.

Use **Research packet** in the project header to choose up to 100 saved papers, 500 notes, and 100 of your approved assistant responses for a focused ZIP export. The packet includes paper metadata and references in JSON/RIS/BibTeX, selected notes with tags and related-source links, and approved responses with citation mappings and Markdown copies. Only your own approved assistant responses are available; collaborators' private histories are excluded.

Use **Export bundle** in the project header to download a ZIP containing project details, references in JSON/RIS/BibTeX, source notes, LaTeX writing files, the review protocol, a document inventory, and saved Python output run snapshots. Run snapshots include selected CSV/TSV contents and are shared project data; review their contents before distributing the ZIP. The original uploaded documents and **your own** assistant conversations are optional and off by default; other collaborators' conversations are never included. The ZIP is a portable data export, not an automatic restore file.

The database (including annotations and project tasks) and uploaded files persist in Docker volumes. To stop the app, press `Ctrl+C`; to start it again, run `docker compose up`. To permanently erase all local research data, explicitly remove the named volumes with `docker compose down --volumes` (this is destructive).

## GitHub Pages deployment

GitHub Pages hosts only the static React frontend; it does not run the FastAPI backend, PostgreSQL, or uploaded-file storage. The included workflow builds and publishes the frontend on pushes to `main` and on manual runs. For a no-cost demo, the API can run on Render Free, with Supabase Free PostgreSQL and a private Storage bucket. This is not a production hosting setup: both providers impose limits, and Render's free service sleeps when idle.

The workflow uses the repository Actions variable `VITE_API_URL` when set; otherwise, it falls back to `https://fieldnotes-api-l1bc.onrender.com`. It tests and builds the frontend before publishing. Set the variable to override the fallback when using a different API host.

The browser retries transient network failures for safe GET requests up to three times to accommodate a sleeping Render Free API. It does not retry writes, and it reports an actionable connection error if the API remains unreachable.

### 1. Create Supabase database and private file bucket

1. Create a Supabase project on its Free plan. Keep the database password private.
2. In **Storage**, create a bucket named `research-documents` and leave it **private**.
3. In **Project Settings → API Keys**, copy the project URL and a **Secret key** beginning with `sb_secret_`. The secret key is privileged: enter it only in Render's backend environment variables; never put it in GitHub variables or frontend code. The backend also accepts the legacy `service_role` key if your project only provides that.
4. Open **Connect** in the project dashboard and copy the **Session pooler** PostgreSQL connection string. Use the pooler rather than the direct database connection for Render's IPv4 network. Its database name should be `postgres`.

### 2. Deploy the API on Render

1. In Render, choose **New → Blueprint**, connect `grace-pasion/ai-research-assistant`, and deploy the repository's `render.yaml`.
2. When prompted, enter the Supabase session-pooler connection string as `DATABASE_URL`, the Supabase project URL as `SUPABASE_URL`, and the `sb_secret_...` key as `SUPABASE_SECRET_KEY`. Enter your OpenAI API key as `OPENAI_API_KEY` for embeddings, semantic ranking, assistant answers, and AI source summaries; the key is optional for accounts, projects, file text extraction, and provider-ranked academic search. Enter your OpenAlex API key as `OPENALEX_API_KEY` to use your account's higher OpenAlex API budget. Do not send secrets in chat or commit them.
3. Render generates a private `JWT_SECRET` for the backend. Leave `STORAGE_BACKEND=supabase`, `SUPABASE_STORAGE_BUCKET=research-documents`, and `CORS_ORIGINS=https://grace-pasion.github.io` as configured by the blueprint. Do not add a Render disk; Supabase Storage is the persistent file store.
4. Wait for the deployment to finish, then open `https://<your-render-service>.onrender.com/api/health`. A healthy service returns `{"status":"ok"}`.

The same Supabase database stores the application's research and literature tables; `LITERATURE_DATABASE_URL` automatically falls back to `DATABASE_URL`. The API creates its tables—including annotations, project and team-workspace invitations, memberships, channels, messages, notifications and per-user notification preferences, the per-project `systematic_review_workspaces` and `paper_study_extractions`, `project_source_summaries`, `project_file_versions`, `python_workspaces`, and `python_workspace_artifacts` tables—adds the username and profile-picture fields to existing accounts, adds the nullable team-workspace link to existing projects, literature-screening fields to existing project-paper tables, collaborator-role/comment-author/annotation-synthesis fields to existing project data, Python source-file and output-provenance columns to existing workspaces, and enables the `vector` extension on startup. The API Docker image installs TeX Live's LaTeX and BibTeX tools for PDF compilation.

### 3. Connect GitHub Pages to the API

1. Optionally, in the GitHub repository, open **Settings → Secrets and variables → Actions → Variables**, then create the repository variable `VITE_API_URL` with the Render service's public HTTPS base URL, such as `https://fieldnotes-api-l1bc.onrender.com`. Do not add `/api` or a trailing slash. The workflow falls back to this Fieldnotes Render URL when the variable is absent. This URL is public configuration; never put API keys or database credentials here.
2. Open **Settings → Pages** and choose **GitHub Actions** as the build and deployment source.
3. Push the changes to `main` (or run **Deploy frontend to GitHub Pages** from **Actions**). Check the workflow result and visit <https://grace-pasion.github.io/ai-research-assistant/>.

Render Free services sleep after 15 minutes without traffic and can take time to wake up. Supabase Free projects may pause after a period of inactivity and have storage/database quotas. Free plans do not provide production uptime guarantees or a reliable backup plan; do not store the only copy of important research there. Check each provider's current limits before deploying.

## Administrator console

1. Create a normal Fieldnotes account for yourself if you do not already have one.
2. In Render, add `ADMIN_EMAILS` as a backend environment variable with the exact email address for that account. Multiple administrator emails can be comma-separated. Keep this setting on the backend; do not add it to GitHub Pages variables. Redeploy the API after changing the allowlist.
3. Open <https://grace-pasion.github.io/ai-research-assistant/?portal=admin> and sign in with that account's existing email and password. This is a separate admin portal, but it does not create a second password or public admin-registration flow. For local development, use `http://localhost:5173/?portal=admin` and set `ADMIN_EMAILS` in `.env`.
4. The dashboard lists account email, joined date, project/document/saved-paper/conversation counts, last recorded activity, and a paginated activity feed. Activity records contain action types and limited operational metadata only: document contents and names, search terms, assistant prompts, and answers are not recorded or displayed. Tracking starts after this version is deployed; previous actions are not backfilled.
5. **Delete** permanently removes the selected account, its projects and research data, activity history, and stored document files. The current administrator cannot delete their own account. If the API cannot remove the user's stored files, it returns an error and does not delete the account.

## Human review and data writes

Generating an assistant response only reads your project data and calls OpenAI; it does not save a research conversation or answer. Direct messages are saved when sent. Each assistant answer uses a generation call and a separate evidence-verification call, so it uses more model latency and tokens than a single-pass answer. The checks lower hallucination risk but cannot guarantee zero errors. Inspect the proposed claims and cited source passages, then select **Approve & save** to store both the question and answer with their source references. **Discard** leaves no research conversation data behind. Saving papers, uploading/deleting files, and editing/deleting projects are direct user actions and take effect immediately.

## Built-in account protections

New registrations require a password of 12–128 characters; a small local denylist blocks common choices and passwords made of one repeated character. Sign-in attempts for both researcher and administrator login are limited to 5 per IP/email pair and 30 per IP per 15 minutes. A successful sign-in clears the matching counters. Rate-limit keys are HMAC-hashed with the backend JWT secret; no raw IP or email is stored in the counters. These controls do not change existing passwords. API responses include security headers, HTTPS responses enable HSTS, and `/api/` responses are marked `no-store`.

## Local development and tests

The easiest supported run path is Docker Compose because it provisions both PostgreSQL databases, pgvector, and Tesseract. If running services outside Docker, use Python 3.12+, Node.js 22+, PostgreSQL 16 with pgvector, and Tesseract on `PATH`; configure the URLs and keys from `.env.example`.

Backend tests:

```powershell
python -m pip install -r backend/requirements.txt -r backend/requirements-dev.txt
Set-Location backend

```

Frontend production build (Node.js 22+):

```powershell

```

## Notes and limitations

- OpenAlex and Crossref are used instead of scraping Google Scholar. Search availability and metadata completeness depend on those public services.
- OCR is performed locally inside the API container. Local Python installs need the Tesseract executable installed separately.
- OpenAI API keys, database passwords, and JWT secrets are read only by the backend. The example secrets are for local setup only; do not expose this development configuration to the public internet.
- The first PostgreSQL container start creates `research_db` and `literature_db`; the API creates tables, including `annotations` and the per-project `systematic_review_workspaces`, adds literature-screening and annotation synthesis columns to existing tables, and creates pgvector indexes on startup. Annotation migration defaults preserve existing notes as untagged and unpinned. The database initialization script only runs for a new Postgres data volume.
- Python runs in browser WebAssembly and loads Pyodide from jsDelivr on first use; the browser needs network access to that CDN. Selected CSV/TSV inputs stay in the browser and are not uploaded by the runner. Project code and generated outputs are persisted by the API; do not use the workspace for heavy training or treat browser execution as a secure environment for untrusted code.
